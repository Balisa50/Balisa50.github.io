The application form is the worst possible interface for hiring and both sides know it. Candidates post CVs into a void. Hiring teams drown in applications they cannot distinguish. The thing that should be happening, someone describing a project and being asked a follow-up, is replaced by a text box that cannot ask anything.

Structured interviews predict job performance roughly twice as well as unstructured ones, and the levers are known: a rubric, anchored rating scales, and consistency across candidates. Those are all things software can do reliably and humans do badly under time pressure.

So HireIQ runs the conversation. It asks a follow-up when an answer is thin, moves on when it is not, and produces a scored report with the reasoning attached.

## Why these calls and not the obvious ones

<TradeOffs>

<TradeOff chose="a small fast model for the interview" over="a frontier model throughout">

Conversational interviewing is high volume and low stakes per token. The reasoning that matters happens once, at scoring, on the full transcript.

Spending frontier pricing on question generation means either charging for the product or running out of budget, and it buys nothing a candidate would notice. Multi-second gaps between questions, on the other hand, are immediately felt and make the whole thing read as a bot quiz. The money goes where the quality is load-bearing, and latency wins everywhere else.

</TradeOff>

<TradeOff chose="temperature zero and a per-criterion rubric for scoring" over="one holistic score">

The first scoring prompt asked for an overall assessment and produced meaningfully different scores for the same transcript on re-runs. A hiring decision that changes when you press the button twice is not a decision.

Scoring one criterion at a time, one to five, with written anchors for what each level means, and aggregating afterwards, fixed it. Generation and scoring want opposite settings, and treating them as one model call with one configuration was the underlying mistake.

</TradeOff>

<TradeOff chose="no login on the apply route" over="requiring an account to interview">

Requiring a candidate to create an account before they can be interviewed loses exactly the candidates who are applying to several roles that evening. The session token lives in the link.

The consequence is that conversation state has to survive a closed tab, so every turn is persisted to local storage and a refresh silently resumes from the last question. An abandoned interview is a wasted model spend and a lost candidate, and connections drop constantly on the networks this has to work on.

</TradeOff>

<TradeOff chose="HTML rendered to PDF" over="composing the PDF directly">

Recruiters live in PDF. They print reports, attach them to applicant tracking systems, and forward them to people who will never open this product.

Generating the report as styled HTML and converting it is much less work than laying out a PDF by hand, and it keeps one template for both the on-screen and the exported version. The alternatives were a low-level PDF library, which means writing layout code, or headless Chrome, which means shipping a browser inside a Python service that has 512 MB to work with.

</TradeOff>

<TradeOff chose="a visible warmup gate" over="letting the first request hang">

The backend sleeps after fifteen idle minutes on the free tier, so the first candidate after a quiet period waits about thirty seconds. Worse, the preflight request fails while the service is still starting, so it surfaces as a CORS error rather than as slowness.

The frontend pings a health endpoint and shows an honest "getting the interview ready" state until it answers. The wait is unchanged. What changes is that the candidate is told a thing is happening instead of watching a dead screen and closing the tab.

</TradeOff>

</TradeOffs>

## What broke

<PostMortem
  title="Wildcard CORS with credentials, shipped twice"
  symptom="Sign-in worked locally and failed in production. Google OAuth would redirect into an infinite loop on some paths, and the API rejected authenticated requests from the deployed frontend with errors that pointed at four different subsystems."
  cause="A wildcard allowed-origin header combined with credentialed requests is silently invalid per the CORS specification. Browsers reject it rather than reporting a configuration error, so the failure surfaces as an opaque network error at the call site. Layered on top were a separate redirect-flow bug in the auth provider and an unrelated race where the auth provider mounted before the route check, briefly flashing a login screen on a public page."
  fix="Explicit hardcoded origins per environment instead of a wildcard, exclude the public apply route from the auth provider entirely, and correct the redirect target in the OAuth flow."
  cost="Two days, most of it spent believing this was one bug in one system rather than three bugs in three."
  lesson="When a symptom spans authentication, hosting and the API at once, the instinct to look for the single common cause is usually wrong. And a specification violation that browsers handle by silently refusing is worse than one that errors, because there is nothing in the console that names it."
/>

<Note>

The provider history is a case study of its own. This has run on three different model providers: the first was dropped for rate limits under traffic spikes, the second for connection failures in production that never reproduced locally, and it now runs on open weights behind a free OpenAI-compatible endpoint. Some configuration keys still carry the second provider's name, which is honest archaeology rather than tidy code.

The related lesson is that the official SDK failing in production while direct HTTP calls worked is not unusual. The library existing is not the same as the library working inside your runtime.

As of July 2026 this one is down at the data layer. The managed database project was deleted and its host no longer resolves, so the frontend and the API both answer and nothing behind them does. It needs a new database and a set of environment variables pointed at it. I would rather say that here than have the probe below report a reachable page and let you assume the product works.

</Note>
