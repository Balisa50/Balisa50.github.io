Every Gambian family has someone abroad sending money home. The Central Bank has internal forecasts of exchange rates and remittance inflows. Ordinary Gambians have nothing: no public forecast, no corridor breakdown, no answer to "what will this hundred pounds be worth when it arrives".

This is the citizens' version. What the Dalasi is doing, where the money comes from, and what the next six months look like with the uncertainty drawn on rather than hidden.

## Why these calls and not the obvious ones

<TradeOffs>

<TradeOff chose="an undocumented Central Bank endpoint" over="a commercial FX API">

The Bank publishes daily indicative rates as an ordinary web page with no documented API. Opening it with the network tab showing revealed a JSON endpoint returning twenty-five years of daily rates, no key required, no rate limit advertised.

Official, authoritative, free, and findable only by curiosity. It became the primary source, with a commercial free-tier API kept alongside purely for cross-validation. For a project about Gambian financial data, sourcing the rates from the Gambian central bank rather than a third-party aggregator is also the difference between a dashboard someone might trust and one they will not.

</TradeOff>

<TradeOff chose="a scheduled job in the repository host" over="the deployment platform's cron">

The platform's free cron runs once a day at a time it chooses. The repository host's scheduler runs on a precise schedule, has free minutes for public repositories, and leaves a visible run log.

More importantly it can commit. The job fetches, cleans, refits, writes the processed CSVs back into the repository and pushes, which triggers the rebuild. The daily commits in the log are that loop running on autopilot, and the data pipeline is version-controlled as a side effect rather than as a feature I had to build.

</TradeOff>

<TradeOff chose="static export" over="server rendering the dashboard">

The data changes once a day, not once a request. Rendering per visitor would mean paying for compute to produce an identical page thousands of times.

Pre-rendering at build time gives instant loads on a 3G connection in Banjul, which is the actual constraint, and costs nothing per visitor. The audience is on mid-range Android phones on slow connections, and a financial dashboard that takes six seconds to paint is a financial dashboard nobody reads.

</TradeOff>

<TradeOff chose="a plain-English paragraph next to the chart" over="the chart alone">

A line with a confidence band is a complete answer for someone who reads charts for a living, and close to useless for the person deciding when to send money.

So every forecast ships with a sentence: the Dalasi has weakened about this much against the Pound this year, the model suggests this range next month, a hundred pounds today buys this and is projected to buy between this and this. The chart is for analysts. The prose is for everyone else, and everyone else is the audience.

</TradeOff>

## What broke

<PostMortem
  title="Two unrelated caching bugs on the same code path, returning rates from the year 2000"
  symptom="The exchange rate endpoint served rates from 2000 instead of the current week. Correct-looking numbers, correct format, twenty-four years stale."
  cause="Two causes stacked. The framework's fetch cache was holding a response captured at build time and serving it indefinitely. Underneath that, the Central Bank's endpoint returns different data depending on the user agent, presumably to discourage scraping, so the un-cached path was also wrong in a second, quieter way."
  fix="Opt that fetch out of the cache explicitly, and send a normal browser user agent with the request."
  cost="Half a day, most of it spent assuming there was one bug."
  lesson="Two bugs on one code path present as one confusing bug. Once the first fix only half worked I should have stopped and asked what else was different between my machine and the deployment, instead of assuming the fix was incomplete."
/>

The other correction that mattered was in the data rather than the code. The Bank's series has a methodology break around 2010 where the calculation changed and rates jump about eight percent overnight, plus occasional duplicate rows from their backend. Fitting across that break produced forecasts with spikes that had no economic meaning. Finding the conversion ratio meant reading methodology footnotes, which is a research task wearing a coding task's clothes.

<Note>

The largest open item is one the write-up used to overstate. The plan was a Prophet and SARIMA ensemble, Prophet specifically because Ramadan and Eid drift eleven days a year against the Gregorian calendar and are therefore invisible to a month-of-year seasonal term. What ships is SARIMA alone. Prophet is named in the exploration notebooks and was never built, so the holiday model is an intention, not a feature, and the comparison I set out to make is still unmade.

</Note>
